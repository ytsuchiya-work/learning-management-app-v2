# learning-management-app-v2

学習塾向けの「生徒成績管理」Databricks App です。成績ダッシュボード、Genie での追加分析、保護者面談で配る **講習 提案書** の自動作成をまとめています。

v2 は、塾が実際に使っている提案書のひな形（以下「提案資料【例】」。スプレッドシート、表面・裏面の2枚構成）に、出力の形と言葉づかいを合わせた版です。v1 の作りは残し、面談資料まわりを作り直しました。

> 本 README に載せている生成結果は、サンプルデータの1名（以下「生徒A」）を匿名化したものです。教室名・生徒コード・点数・診断内容の原文は載せていません。

## 1. 構成

| 項目 | 内容 |
|---|---|
| 画面 | React（Vite + TypeScript）＋ recharts |
| サーバー | FastAPI 1プロセス。`/api/*` と、ビルド済みの `client/dist` を同じプロセスで配信 |
| データ | Unity Catalog のテーブル（オープン模試 `c_test_results`、単元別の学習記録 `pcs_results`）と Volume（学習行動診断 ETS の PDF、講習SSS の xlsx） |
| LLM | Unity Catalog のモデルサービス（Claude Opus 5.5）を AI Gateway `/ai-gateway/mlflow/v1/chat/completions` 経由で呼び出す |
| PDF 読み取り | `ai_parse_document()`（SQL ウェアハウスで実行） |
| 追加分析 | Genie スペース（会話 API と Agent モード） |
| 長時間処理 | 生成は WebSocket（Databricks Apps のプロキシ 120 秒制限を回避） |

タブは「デモシナリオ」「成績ダッシュボード」「保護者面談資料」の3つです。

## 2. v1 との差分

| 観点 | v1 | v2 |
|---|---|---|
| 資料の位置づけ | 面談用の分析資料。教科ごとに単元を提案するが、コマ数の提案で締めない | **講習 提案書**。表題は「○○ 様 講習 提案書」、裏面の提案コマ数で締める |
| 章立て | 目標・1〜5章（他教科・備考なし） | 提案資料【例】と同じ：目標／1. 全体成績推移 (オープン模試分析)／2. 志望校ギャップ・課題／3. 学習特性・行動評価 (ETS)／4. 英語：現状分析／5. 数学：現状分析／**6. 他教科の所見**／**備考** |
| 各章の型 | 自由。3〜5章は500〜600字で、小見出しと箇条書きが混在 | 各章「・」4行、1行70〜85字。順序は「良い点 → あと一歩 → これから伸ばす点 → 今後は、」 |
| 目標の書き方 | 長期・中期・短期の数値目標 | 取り組む姿勢と方針を3段落の文章で書く（偏差値などの数値目標は2章へ） |
| 語り口 | 既定のトーンは「② 標準」 | 既定は「① 励まし重視」。下がった点も「一時的な揺り戻し」「これから積み上げたいポイント」と書く |
| 用語 | 本文に「PCS」「定着率20%」「全128単元」、データの表記ゆれの話まで出る | 保護者向けに言い換える（PCS→「これまでの単元別の学習記録」、ETS→「学習行動診断」）。集計値、テーブル名、データの不備は本文に書かず、担当者用メモにだけ書く |
| 模試の時期 | 「中1 第3回」 | 「中1 8月」（提案資料【例】の表記に合わせる） |
| 入力欄 | 志望校・現状偏差値・目標偏差値 | ＋生徒名、学科・コース、判定、学校の定期テスト（任意）、提案コマ数（個別・集団・5教科以外） |
| 裏面 | なし | 提案コマ数・詳細（個別は教科ごとに単元とコマ数、集団・その他、5教科以外）、オープン模試の折れ線グラフと推移表 |
| コマ数の配分 | なし（「面談で相談」と書くだけ） | 入力した個別コマ数を、AI が未定着・一部定着の単元に配分する。合計はサーバー側で入力値に必ず一致させる（`_fix_koma_units`）。画面で編集可能 |
| 印刷 | A3横1枚・2段組の文章のみ。各章末に「参照：テーブル名」 | **表面・裏面の2ページ**（既定 A3縦、A4縦も可）。はみ出す面だけ文字を自動で縮めて1ページに収める。注記は「※PCS・オープン模試の結果より分析」「※最新のETSは{年月}時点のデータです。」 |
| 出典の表示 | 画面・印刷とも、テーブル名・ドキュメント名 | 画面はテーブル名・ドキュメント名（追跡用）、印刷は保護者向けの注記 |
| 単元データの渡し方 | 先頭50件だけを LLM に渡していた | 全単元を教科別・定着度別にまとめて渡す |
| 単元の重複 | 表記ゆれ（「1次関数」と「一次関数」など）で同じ設問が二重に数えられる | 単元を `(教科, 大単元NO, 連番)` で識別し、設問は重複を除いて数える（生徒Aでは 236件 → 117単元） |
| ETS の読み取り | 抽出テキストを2,500字で切っていたため、ETS が勧める改善点（2ページ目）が LLM に届かない | 7,000字まで渡す。「学習の習慣」「結果を反省する力」など、ETS が勧める伸ばしどころを4行目に入れる |
| ETS の強み・伸ばしどころ | 区別の指示なし | 本文で「優れている」とされた力だけを強みとし、「あなたに必要なもの」「こうすればもっと成績は上がる」の項目は伸ばしどころとして書く。項目名は診断の表記どおり「」で書く |
| LLM の呼び出し | `max_tokens=8000` | `max_tokens=32000`、`reasoning_effort="medium"`（理由は「6. 既知の注意点」） |
| Genie で修正 | 修正後も型の指定なし | 修正後も「・」4行の型と保護者向けの言葉を保つ |

## 3. 提案資料【例】との比較

### 3-1. v1 で見つかった差分

v1 の出力と提案資料【例】を、同じ生徒（生徒A）で比べた結果です。

**章立てと紙面**

- 目標と1〜5章の見出しは、1対1で対応していた。
- 「6. 他教科の所見」「備考」、裏面（提案コマ数表と模試の推移グラフ・表）、判定欄が無かった。

**資料の作り（大枠）**

| 観点 | 判定 | 内容 |
|---|---|---|
| 資料の目的 | × | 提案資料【例】はコマ数の提案で締めるが、v1 は分析資料止まり |
| 紙面構成 | × | 提案資料【例】は表面＝文章、裏面＝表とグラフ。v1 は文章だけ |
| 用語 | × | v1 は本文に内部用語や集計値が出る。印刷にテーブル名が載る |
| 各章の型 | △ | 提案資料【例】は全章4行・約320字に固定。v1 は3〜5章が約2倍の長さ |
| 語り口・数字の量・目標の書き方 | △ | v1 は率直で数字が多く、目標は数値目標 |
| 章の流れ・読み手・根拠を示す考え方 | ◎／○ | 合っていた |

**内容**

- 学習行動診断（ETS）の読み取りは、原本と照らすと v1 の方が正確だった。
  - 提案資料【例】は、ETS で「必要なもの」とされた項目を強みとして書いていた。
  - 提案資料【例】は、高い値の項目を課題として書いていた。
- 提案資料【例】には、単元別の学習記録に無い単元名が含まれていた。定着度の判定がデータと合わない単元もあった。

### 3-2. v2 で合わせたこと・合わせられないこと

| 区分 | 内容 |
|---|---|
| 合わせた | 章立て・見出し・注記、各章4行の型、語り口、用語の言い換え、月表記、表題と志望校の行、裏面（コマ数表・グラフ・推移表）、定期テストへの言及、6章・備考 |
| 入力すれば合う | 生徒名、学科・コース、判定、定期テストの点数と目標、提案コマ数（データに無い情報のため手入力） |
| 合わせていない | 模試の数値。一部の回で提案資料【例】と DB の値が違う（ある回の数学・国語・5科合計、別の回の社会）。v2 は **DB の値を正として出す** |
| 合わせていない | 単元名・定着度。v2 は単元別の学習記録にある単元と判定だけを書く（データに無い単元は書かない） |
| 合わせていない | ETS の強み・伸ばしどころ。v2 は診断の原本に沿って書く |

## 4. v2 の検証結果

デプロイ先で、生徒Aに提案資料【例】と同じ条件（志望校・学科コース・判定・定期テスト・提案コマ数）を入れて生成しました。

| 確認項目 | 結果 |
|---|---|
| 所要時間（WebSocket 経由、ETS 解析を含む） | 約99秒 |
| 章の型 | 1〜6章すべて「・」4行、1行73〜83字。目標は3段落 |
| 保護者向けの言葉 | 本文に「PCS」「定着率」「第N回」「テーブル名」「表記ゆれ」「単元中」は0件 |
| 模試の時期 | 「中学2年生の4月」のような月表記 |
| 提案コマ数 | 入力どおり（個別は英語25・数学22、集団は国語・理科・社会が各12、5教科以外はリスニング・スピーキング）。単元ごとの配分の合計も入力値と一致 |
| 学習行動診断 | 原本の本文で「優れている」とされた力を強みに、ETS が勧める「学習の習慣」「結果を反省する力」を4行目の伸ばしどころに書いた |
| 備考 | 空欄（教室長が記入する欄） |
| 印刷（A3縦） | 表面1ページ・裏面1ページ。A4縦でも文字を自動で縮めて各1ページに収まった |
| 担当者用メモ | データの欠損や不整合（未受験の回、診断の学年と模試の年度のずれなど）はメモにだけ出た |

生成結果（表面の一部。生徒Aを匿名化し、固有名と点数は伏せ字・要約にしています）:

```
【2. 志望校ギャップ・課題】
・志望校の○○高校△△コースは□判定で、現状偏差値48から目標偏差値55まで、7.0の差です。…
・学校の定期テストでは英語・数学とも、目標まであと数点と、あと一歩で仕上がる状態です。…
・これまでの単元別の学習記録では、…などがしっかり定着しており、入試にもつながる大切な土台になっています。
・今後は、定着している単元を応用問題や入試形式の実践演習で得点力に変え、偏差値の差を…着実に縮めていきます。
```

LLM の出力は生成のたびに多少変わります。ただし行数・字数の型と用語のルールは、上の条件で毎回守られることを確認しています（ローカル3回・デプロイ先1回）。

## 5. デプロイ

### 5-1. 初回のみ

1. アプリを作成し、リソースとして SQL ウェアハウス（`CAN_USE`）と Genie スペース（`CAN_RUN`）を付ける。
   - `app.yaml` の `resources:` は、既存のアプリには反映されない。作成時の JSON で指定する。
2. アプリのサービスプリンシパルに、Unity Catalog の権限を付ける。

```bash
SP=<app の service_principal_client_id>
databricks grants update catalog <catalog> --json '{"changes":[{"principal":"'$SP'","add":["USE_CATALOG"]}]}'
databricks grants update schema <catalog>.<schema> --json '{"changes":[{"principal":"'$SP'","add":["USE_SCHEMA","SELECT"]}]}'
databricks grants update volume <catalog>.<schema>.ets --json '{"changes":[{"principal":"'$SP'","add":["READ_VOLUME"]}]}'
databricks grants update volume <catalog>.<schema>.sss --json '{"changes":[{"principal":"'$SP'","add":["READ_VOLUME"]}]}'
databricks grants update model_service <catalog>.<schema>.<model_service> --json '{"changes":[{"principal":"'$SP'","add":["EXECUTE"]}]}'
```

Volume の `READ_VOLUME` は、テーブルの `SELECT` とは別に必要です。

### 5-2. 毎回

```bash
./deploy.sh <databricks-profile> [app-name] [workspace-path]
```

`deploy.sh` が行うこと:

1. `client/` をビルドする。
2. 実行に必要な `server.py`・`app.yaml`・`requirements.txt`・`client/dist` だけを `.deploy/` に集める。
3. `databricks sync` でワークスペースに送り、`databricks apps deploy` する。

接続先（ウェアハウス・Genie スペース・カタログ・モデルサービス）は `app.yaml` の `env` で切り替えます。

### 5-3. ローカルで動かす

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
(cd client && npm install && npm run build)
DATABRICKS_CONFIG_PROFILE=<profile> DATABRICKS_APP_PORT=8000 .venv/bin/python server.py
```

## 6. 既知の注意点

- **思考トークンで本文が切れる。** 行数・字数を細かく指定すると、Opus 5.5 が `max_tokens=8000` を思考で使い切り、本文が途中で終わる（`finish_reason=length`）。
  - 対策：`max_tokens=32000`、`reasoning_effort="medium"` にした。
  - `thinking.type=disabled` は、このモデルでは 400 になる。
- **実施月はデータに無い。** 提案資料【例】の対応（第1回=4月、第3回=8月、第7回=1月）を `KAISU_MONTH` に固定している。対応の分からない回（第2回など）は「第N回」のまま出る。
- **ETS の PDF は画像。** `ai_parse_document()` はグラフの値までは読めない。強みと伸ばしどころは、主に本文の文章から判断している。
- **長時間の生成は WebSocket で行う。** HTTP では Apps のプロキシ 120 秒制限に当たる。WebSocket が開けないときだけ HTTP にフォールバックする。
- **SDK の再送に注意。** `api_client.do` は 60 秒で同じリクエストを自動再送する。長い生成が二重に課金されるため、`requests` で1回だけ呼んでいる（`_chat_llm`）。
- **`client/package-lock.json` は公開レジストリの URL で記録している。** 社内プロキシなど別のレジストリを使う場合は、npm の既定設定（`replace-registry-host=npmjs`）で読み替えられる。
